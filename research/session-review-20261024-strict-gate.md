The named H33 result `0.2778` appears in the user-provided site inventory and repo lineage audit as a **USER-REPORTED claim**; there is no organizer submission-page receipt in this checkout, so it is not `ORGANIZER-CONFIRMED`. Raster forensics support a plausible metric mechanism, but do not prove either the claim's authenticity or its causal attribution:

1. The H19-5 → D2.8 → SOLO-D2.8 → H33 sequence is a nested thinning/collar lineage. Raster set comparisons show no new positive pixels in the H33 step: 6,436 dots removed relative to D2.8 are within two pixels of the mapped catalogue. See [`docs/research/session-20261024-audit-why-0.2778.md`](../docs/research/session-20261024-audit-why-0.2778.md) and [`evidence/h33_forensics_20261024.json`](../evidence/h33_forensics_20261024.json).
2. The competition metric uses a 300 m triangular kernel and weights false negatives more heavily than false positives (`α=0.2`, `β=0.8`), as stated on the official [DrivenData problem page](https://www.drivendata.org/competitions/306/competition-doe-gems/page/967/). Well-spaced predictions can preserve line coverage while eliminating redundant nearby points; removing near-catalogue points can also reduce false-positive mass if known/catalogued faults are masked in the live evaluation. These are plausible mechanisms, not evidence that the local component holdout predicts private/live performance.
3. The repo's H33 geometry/claim association is descriptive, based on a small, lineage-linked set and owner-reported scores. It is not a causal model and should not be extrapolated as “distance from catalogue always improves score.” The local hide-and-recover protocol withholds mapped faults, whereas the competition page says prize labels are newly mapped faults not already in the public catalogue: that domain shift is material.

The public leaderboard was re-opened from its official URL at `2026-10-24T19:22:59Z`. Snapshot: #1 `0.4413`; #5 `0.3539`; #50 `0.2818`. Consequently, the prompt's “0.3195 current high” is stale, and user-reported H33 `0.2778` is below the public rank-50 snapshot at the time checked. ### Why the top proposal was not run here

The explicit instruction says stop if more than 70% of candidate dots lie within 3 px of any registry raster. The restored hash-pinned witness (see [`registry/data_manifest.json`](../registry/data_manifest.json) and `data/registry/dense_17gemdoe.tif`) has positive support on all valid footprint cells: its 3-px coverage of the footprint is 100%. Therefore every nonempty candidate emitted inside the legal footprint necessarily fails the literal 70% rule, before its own feature ranking could affect the outcome. The requested “single method paragraph” also is absent from the prompt block; no existing lane is assumed to be that missing assignment. Under **Maximize P(Win)** and **Own the Outcome**, it would be misleading to create another nonempty TIFF, call it unique, or spend compute/slot budget while this gate is binding. The prior MDPS-88 feature stack already tested 44 feature-alone canaries (max symmetric AUC `0.5947545`, threshold `0.90`); these do not validate the new χ-coherence hypothesis.

Resolve the protocol problem explicitly in the shared project policy before another candidate build: either (a) keep the literal rule and accept that no non-empty submission can ever clear uniqueness, or (b) have the project owner authorize a revised discriminative similarity metric in the standing prompt. An agent must not silently choose (b). Under the current literal instructions the correct answer is **no submit-ready unique TIF can be produced**. The existing research TIFF remains easy to download and is clearly marked research-only / duplicate / DO NOT SUBMIT.
