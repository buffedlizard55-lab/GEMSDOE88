Why H33 scored 0.2778 — the forensic answer

A subtraction lineage, not a better model.

H33 (CLAIM 0.2778, 37,654 dots) is a strict subset of SOLO-D2.8 (40,199) ⊂ D2.8 (44,090) ⊂ H19-5 (121,131). Every step after D2.8 removed only dots within 2 px of the catalogue. H33 has 0% within 2 px, median 19.65 px, 41.7% beyond 25 px, spacing median 3.0 px (min 2.83 px). Kernel algebra: DTI rewards many well-separated dots that each own private 300 m kernel; two adjacent dots share kernel (T saturates, S grows) so spacing ≈ kernel radius wins. Removing a dot with marginal credit <0.2·DTI always helps — at DTI 0.28 that bar is 0.0556. Reported gains along the chain (0.192 → 0.247 → 0.260 → 0.270 → 0.277) are attributable to removed collar dots. Across 13 ledger rasters, Spearman(median distance to catalogue, CLAIM) = 0.891 (descriptive, n=13). Footprint baseline: 47.2% of allowed cells are >25 px from catalogue; low scorers hug it (GEMSDOE81 median 2.2 px → 0.0041). Can we beat 0.2778? Not demonstrable locally: hide-and-recover scores H33-class rasters at ~0 by construction, and no instrument here rank-orders high public scores except the distance fingerprint (LOO RMSE 0.036). Gap to #5 (0.3539) needs +27–29% more kernel credit, to #1 (0.4413) +59–63%. Only a portal receipt can tell.

Why “Predicted values must be in range [0, 1]” will not happen here

The three suspects are removed at once

This portal error is unproven in organizer code, but we remove all three local causes that can trigger it: (1) NaN anywhere (fails (a≥0)&(a≤1) when nodata is undeclared), (2) values a hair outside [0,1], (3) reader-incompatible layout. The writer mirrors the official sample: single-band float32, LZW, striped, 1-row strips, classic TIFF, no predictor, nodata=None, zeros outside footprint. Outside the footprint the file holds 0.0 — the public spec permits “null or nan” there and a zero prediction contributes nothing to DTI.

Executive submission guide — exact portal steps

How to submit if a future run card says promote

CHIASM-88 is not promoted. The steps below are for a future candidate that passes the like-for-like holdout, uniqueness and format gates and is selector-approved. Never submit a DO-NOT-SUBMIT file.

  1. Require a positive paired blocked result

    Whole fault components, 3-px feature buffer, visible-only catalogue features, pixel-exact known mask, gems57-pooled-hide-v2, and a paired 95% CI above zero vs the incumbent on the same seeds.

  2. Require both uniqueness phases under the authorized rule

    Preplacement surface |ρ|≤0.90 and final 3-px forward overlap ≤0.70 (dense surfaces via ρ, sparse dotfields via overlap — the like-for-like reading; literal any-raster 1.0 is recorded but degenerate). Never invent a silent exemption.

  3. Run the fail-closed validator

    python scripts/validate_release.py --require-submit must exit 0 (default exits 0 for research-valid but negative; --require-submit exits 2 while any gate is negative). The authenticated organizer template must match the pinned grid (2176d08e...).

  4. Upload exactly one file

    On drivendata.org/competitions/306/competition-doe-gems/submissions/ sign in → File to submit: choose the .tif or a .zip holding exactly one GeoTIFF (no folder). Must be single-band float32 in [0,1], EPSG:32611 at 100 m, 3730×3292, same transform as sample_submission.tif. Our writer guarantees nodata=None and zeros outside footprint.

  5. Paste the note (optional, 140 chars max)

    Copy the run card’s submission_note verbatim — it makes the portal receipt auditable. Example: CHIASM chi-slope-basin 37654 dots; HOLDOUT-DTI 0.0671; UNSCORED; DO NOT SUBMIT (78/140). The portal has no “name” field — name is for your ledger only.

  6. Create submission, record receipt

    Click Create (or equivalent) once. The portal returns a receipt with ORGANIZER-CONFIRMED public DTI. Immediately append it to ledger/submissions.csv and to research/lbcal_user_reported_scores_*.tsv, then refit the receipt model. Never relabel HOLDOUT-DTI as organizer score.
