Experiment 01 · what the holdout actually selected

The kernel-disjointness premise is falsified: tighter dot packing wins monotonically, because the official DTI charges false positives per DOT, not per unit of kernel area.

KDMC-88 preregistered that a >=6 px kernel-disjoint packing would beat the registry's ~3 px fields, on the argument that overlapping 300 m kernels pay for the same area twice. Reading vendor/gems57/metric.py line by line shows the false-positive term is FP_w = sum_x p(x)*(1 - k_self(x)): it is charged once per emitted dot and is completely independent of how much two dots' kernels overlap. Overlap costs nothing; only the dot count does. Because the true-positive term credits each truth pixel with the MAXIMUM kernel weight over all dots, and the truth is a set of one-pixel-wide lineaments, dots spaced 6 px apart leave the midpoints of a line uncovered (k(3)=0) while dots at 2.83 px keep every truth pixel within 1.41 px (k=0.53). The holdout confirms the algebra exactly: at a matched budget the score falls monotonically as separation grows, and the optimum sits at the tightest separation tested with roughly 1% of allowed cells emitted.

Automatic uniqueness · every pinned prior raster

Chance-corrected overlap, so a space-filling prior cannot veto everything

Fixed this session (IR-88-73). One prior in the inventory (17GEMSDOE) is positive on every cell of the footprint, so its 3 px halo covers 100% of the allowed domain. The literal "70% of my dots within 3 px of theirs" test therefore returns 1.0000 for every possible candidate, including one built from unrelated physics — it carries zero information and permanently blocked every candidate. The shared template now also reports excess = (overlap − halo) / (1 − halo), which equals the literal test when the prior has no halo advantage, is stricter in relative terms otherwise, and is undefined exactly when the prior cannot discriminate. For such a prior the protocol's rank-correlation test (|ρ| ≤ 0.90) is the binding one, and this candidate passes it at 0.1031.

Honest limits

What this page does not claim

  • No organizer receipt exists for any file in this repository, so every figure here is HOLDOUT-DTI, PROXY or MODEL and none of them is a leaderboard score.
  • The holdout hides whole MAPPED fault components; the competition target is UNMAPPED faults. The holdout is the best available unbiased instrument, not the real task.
  • drivendata.org is unreachable from the build sandbox, so the public leaderboard value and the remaining weekly-slot balance cannot be verified here and are carried as UNVERIFIED human-supplied inputs.
  • metric.py's claim that the organizer masks mapped catalogue faults out of scoring traces to a forum thread that cannot be re-read from here; the candidate is built to be correct either way by emitting zero mass on mapped faults.
  • src/gems88/features.py cannot run on a clean checkout (IR-88-72): it requires acquisition_block_id_100m.tif and tiger_road_distance_m.tif, which exist in no pinned source. This lane therefore uses its own self-contained feature builder.
  • Two cores and 3 GB of RAM are available, so model capacity (250-iteration histogram gradient boosting) and the number of hide draws are compute-limited, not design-limited.
  • The blocked holdout CANNOT rank the catalogue-collar choice: every collar arm scores exactly 0.00000 there because the holdout's truth is withheld catalogue geometry. That question is answered only by the off-catalogue SGMC proxy, which is a PROXY.
