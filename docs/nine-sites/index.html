Why the highest file (GEMSDOE32, 0.2778) scores highest - evidence and limits

The H33 file is a strict subset of the D2.8 dots used by GEMSDOE25 and GEMSDOE30: the bytes give 37,654 H33 dots against 44,090 D2.8 dots, with 6,436 removed. Subset: True. Removed dots within 1 px of the catalogue: 3,891; between 1 and 2 px: 2,545; beyond 2 px: 0. H33's closest dot to the catalogue is 2.24 px.

Because H33 is a subset, it cannot recover any fault that D2.8 misses. Any score difference comes from the removed dots. Under the metric (alpha 0.2 on false positives, beta 0.8 on false negatives), removing one dot with true-positive weight d and false-positive weight f improves DTI only when f/d > (0.8*TP + 0.2*FP + 0.8*FN) / (0.2*TP). This is derived from the metric and checked numerically: at the official worked example (TP 3.00, FP 1.89, FN 2.00) the break-even ratio is 7.3. The user-reported gain over D2.8 is 0.2778 minus 0.2600 = 0.0178. It is a public-split figure with no receipt, and the public label set size is not published here, so its noise cannot be quantified.

GEMSDOE25 and GEMSDOE30 hold the same 44,090 dots (overlap 1.000 both ways) and both report 0.2600. That agreement is consistent with one dot set being submitted under two site names.

The repo's own collar-versus-visible holdout (registry/con88_collar_holdout.json, HOLDOUT-DTI, gems57-pooled-hide-v2) gave a paired delta of +1.0e-6, 95% CI [-7.9e-9, +3.2e-6]. That is negligible, so collar removal is not established as the mechanism. The H33 advantage is therefore UNEXPLAINED by available holdout evidence.

Irregularities for review

  • Scores in the prompt are USER-REPORTED. No organizer receipt exists in the repo.
  • GEMSDOE25 and GEMSDOE30 hold identical dot sets (44,090 dots; both report 0.2600). Two site names point to the same submission content.
  • The official text allows NaN or null outside the bounds. Five winner files use NaN outside the footprint. Four (GEMSDOE30, 32, 33, 36) use zeros outside it. That is a literal deviation from the rule text, but the user reports that these files were scored.
  • The portal error "Predicted values must be in range [0, 1]" is not explained by these bytes: every winner file's finite values lie in [0, 1]. The cause is unknown.
  • The project's stricter local "full-grid finite" check fails the current GEMSDOE30 HEAD file (7,111,787 NaN outside the footprint). That is a repo-stricter rule, not an official one.
  • The parallel-run protocol's 0.70 overlap rule was applied to dot sets. The witness is a continuous probability map (median 0.22, max 0.98). Its "dots" are defined by p > 0, which covers the whole footprint. This representation choice is the owner's decision, not the agent's.
