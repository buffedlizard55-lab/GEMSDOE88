How to submit (portal form)

  1. Open the submissions page

    Go to drivendata.org/competitions/306/competition-doe-gems/submissions/ and sign in with the team account.

  2. Choose the file

    Upload either the .tif or the .zip. The zip holds exactly one GeoTIFF.

    The file must be a single-band float32 raster with values in [0, 1], EPSG:32611 at 100 m, and the same shape and geotransform as sample_submission.tif (3730 × 3292, origin 243350 / 4508550). Every file here is written with nodata = None and zeros outside the footprint. That is why it cannot trigger the portal error “Predicted values must be in range [0, 1]”, which comes from −3.4e38 or NaN fill values.

  3. Paste the note (optional, 140 characters max)

    For LBCAL: LBCAL receipt-calibrated q, 38278 dots, <=66% in sibling halos; HOLDOUT 0.0616; model-proj only, UNSCORED

  4. Submit once and record the receipt

    The cap is 3 submissions per rolling 7 days. After submitting, add the portal score and date to ledger/submissions.csv, which turns the row from MODEL to ORGANIZER-CONFIRMED.

    The rules also require you to choose your final submission without knowing its private score, so pick it on evidence, not on public-LB chasing.

Limitations and access we need

What could make this wrong

  • The receipts are user-reported. We hold no portal receipts. 5 of the 111 scores had no raster on GitHub, and 2 rasters had NaN across the footprint and were excluded.
  • The receipt-model error is real. Its CV RMSE is about 0.031, so projections are rankings with error bars, not scores. It also under-predicts the gems70, gate_ortho and tiltworm family by 0.09–0.12, which means some localiser is still missing.
  • The holdout targets the wrong faults. Hide-and-recover tests catalogue faults. The new test faults evidently differ, since near-catalogue lanes fail on the LB.
  • Access we lack: the 1 m USGS 3DEP / GeoDAWN LiDAR (prd-tnm S3) is not reachable from this sandbox. That blocks 20 m scarp models of the kind leader #5 reports using.
