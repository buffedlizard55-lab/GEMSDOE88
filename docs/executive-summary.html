GEMSDOE32 H33: why it reported 0.2778 and whether we can beat it

H33 lineage JSON ↗ · H33 collar JSON ↗

What H33 actually is

h33-h33-2-b2-20261004T220000Z-e5eb6e7e-zeros is a binary raster with exactly 37,654 positive pixels (the -zeros suffix is a naming convention, not an all-zero array). Every dot lies outside 200 m of existing_faults.tif — it is an off-catalogue, off-footprint-edge point pattern. It is an exact 0-px subset of the SOLO-D2.8 arm: the D2.8 Poisson-thinned H19-5 ridge skeleton with B=1 collar pruning, minus 2,545 dots in the 1<d_cat≤2 px annulus and minus 6,436 dots at d_cat≤2 px. Its positive support is therefore nested inside the same H19-5/D1.5/D2.8 family that produces GEMSDOE24, 25, 27, 28, 30, 31, 33 and 36.

Why it may have reported 0.2778

The user-reported value 0.2778 carries no organizer receipt (GEMSDOE32's registry explicitly records "NO ORGANISER SCORE EXISTS"), so it cannot be treated as a verified leaderboard score. Two geostatistical mechanisms could produce a relatively high value for a sparse off-catalogue point pattern under the competition's Tversky-style DTI with alpha=0.2, beta=0.8:

  1. FN-weighted reward. With beta=0.8, the metric penalizes missed faults (FN) more heavily than false alarms (FP). A very sparse prediction that happens to coincide with a small number of withheld true faults can achieve moderate DTI while incurring little FP penalty — especially if the hidden label set is itself sparse.
  2. Degenerate empty/near-empty prediction. A prediction with few or no positive pixels yields TP≈0, FP≈0, and FN equal to all withheld positives. Depending on the exact metric normalization and how the empty case is handled, this can produce a non-zero but structurally meaningless score. The -zeros naming is consistent with this possibility but cannot be confirmed without the organizer's scoring code and labels.

In either case, 0.2778 is not evidence of geological discovery; it is a user-reported claim on a raster nested in a known catalogue-derived lineage.

Can we generate something that scores higher?

Not under the current binding protocol. The dense witness covers 100% of allowed cells, so any new nonempty raster — including a geothermally-motivated one like GTZ-88 — is blocked before feature construction, holdout fitting, or scoring. Even if unblocked, beating a user-reported 0.2778 would require a genuinely distinct, holdout-validated signal. The entire focus-site fleet converges on one ridge-pruning family; GTZ-88 deliberately breaks that lineage (2.93% H19-5 overlap vs 97.75–100%) but remains blocked by the registry witness, not by scientific inferiority.

Procedure — for a future cleared candidate only

Exact DrivenData submission steps

  1. Require machine approval

    Open that candidate's run card. Require ok_to_submit: true, every scientific/uniqueness/format gate true, a unique name and note of at most 140 characters, and validate_release.py --require-submit exit 0. Any failure means stop. Today: no candidate passes.

  2. Verify the downloaded bytes

    Compute SHA-256 and require an exact match to the run card. A changed filename or hash alone is not evidence of uniqueness. The TIFF must be single-band and match the organizer sample's CRS (EPSG:32611), shape (3730×3292), and geotransform.

  3. Upload exactly one artifact

    Sign in to the DrivenData submissions page. Choose either the approved .tif or its ZIP containing exactly one TIFF. Never select a file whose name contains DO-NOT-SUBMIT.

  4. Paste the approved name and note

    Use the exact fields from the green run card. Confirm the note is no more than 140 characters and the portal's current weekly quota allows the slot.

  5. Submit once and archive the receipt

    Only a value copied from the resulting portal receipt may be called ORGANIZER-CONFIRMED. HOLDOUT-DTI and model projections are not leaderboard scores.
