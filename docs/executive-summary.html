How a submission is made (only when every gate passes)

  1. Check the machine decision first. Open the candidate's JSON run card and require ok_to_submit: true with every gate true, then re-run its validator (for the current file: python scripts/validate_mdps88.py --require-submit — today it correctly exits 2). If it exits non-zero, stop: do not upload anything.
  2. Download one file. Use the approved single-band .tif itself, or the .zip that contains exactly that one TIFF (byte-identical member, verified).
  3. Open the official page and sign in with the team account: drivendata.org/competitions/306/competition-doe-gems/submissions/. Confirm the weekly limit shown on the portal before using a slot — the separate human selector owns that decision.
  4. Upload, name, note. Choose the downloaded file, give the submission its unique name from the run card, and paste its note (at most 140 characters) so the team can tell submissions apart later.
  5. Submit once, then archive the receipt. Only a score copied from that portal receipt may be labelled ORGANIZER-CONFIRMED. Local HOLDOUT-DTI numbers are never leaderboard scores.

About the portal error “Predicted values must be in range [0, 1]”: files that store NaN (or a nodata sentinel such as −9999) outside the study-area footprint can trip this check, because the non-finite/out-of-range cells are still in the raster. Every file published here uses the strict “zeros” encoding instead: all 12,279,160 cells finite, values only in [0,1], 0 outside the footprint, nodata unset — verified on the written bytes by two independent validators (min 0.0, max 1.0). If a future download does not say that, do not upload it.
